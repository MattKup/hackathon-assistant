# Журнал: анализатор противоречий (ветка s6-conflicts)

Формат: что проверял → что нашёл → решение и причина → что отбросил.

## 26.11 — проектирование и кандидаты (локально, BM25/tf-idf, без стенда)

1. **Окна и метаданные.** Проверил `registry.build.run` на корпусе: 709 окон (TECH 185, ИБ пресейл 116, ИБ проект 241, ДБРЦТ 167), 96 окон — заголовки разделов (`kind=section_title`). → Заголовки исключаю из пар (не несут правил).
2. **Кандидаты только по tf-idf соседям (k=8 в корзине отношения).** Из 13 эталонных пар (7 кандидатов) 6 вообще не попали в кандидаты: пункты про одно действие написаны разными словами (2.18 «назначается Ресурсный менеджер для выделения РП» ↔ 4.1 «за назначение РП отвечает Руководитель ОУП», cos 0.13). → Добавил второй канал: **блокировка по действию** (общее действие внутри документа/дирекции, ≤ 10 партнёров на окно с сильным сигналом). Цена — квадрат размера блока внутри дирекции, а не всей базы. Отбросил полный перебор пар внутри дирекции: при 300 документах дорого для общей политики ↔ всё.
3. **Сигналы на уровне пункта давали шум** (длинный пункт-список «совпадал» со всем: IB 4.2.3, 24.7.4). → Сигналы привязаны к ключам «действие + роль/объект» **внутри предложения**; общий ключ (только действие) весит 0.5, кроме редких действий («приоритет»); поправка на длину; скор = сигналы × близость темы. Отбросил ранжирование «чистой близостью» (×3 sim): наверх шли соседние пункты-шаги.
4. **Новые сигналы по эталонным случаям:** `status_vs_action` (24.4 «закрывает карточку в CRM» ↔ 24.5 «статус «Ожидает закрытия»»), `precondition_diff` (ДБРЦТ 10.1 «после подписания договора создаёт проект» ↔ 10.2.1 «после согласования сметы создаёт проект»). Риск подгонки под 7 ориентиров записан: сигналы общие (статус/порядок событий), не завязаны на конкретные пункты.
5. **Отбор под бюджет:** доля 20 % на пары разных дирекций; одно окно ≤ 6 раз (хабы вроде TECH 9.2 иначе съедают бюджет). Локально: 8028 пар-кандидатов → 562 после фильтра → 300 к LLM; в 300 попадают пары 6 из 7 ориентиров на уровне кандидатов (нет: 22.3↔24.3 — только слабый сигнал «условие ↔ правило», близость 0.17; 7.4↔9.2 — ранг 233, но 9.2 исчерпал лимит).
6. **Судья:** JSON-схема с порядком полей ситуация → цитаты → объяснение → kind (рассуждение до вердикта). Строгость: «сомневаешься — понижай». Вид по отношению пар задаёт код: разные дирекции → `dept_difference` (противоречия по определению нет), одна дирекция + `dept_difference` → `none`.
7. **Проверки кодом:** цитаты — `norm`/`repair_quote`, допускаю перестановку A↔B (модель путает); числа объяснения должны быть в текстах пунктов. Нашёл ошибку разбиения на предложения после номера пункта («5.2. После…» резалось на «5.2.») → исправил.
8. **Зависимости кодом без LLM:** внешние отсылки (`external_refs`) — 5, ссылки на другие пункты («в рамках п. 8.4») — 4.

## 26.11 — прогон 1 на стенде (runs/20261126T131030Z-conflicts, коммит 350df86, бюджет 700, эмбеддинги bge-m3)

Отбросил второй вызов-проверку LLM на каждую находку: удваивает стоимость, а ручная разметка — задача службы качества.

## 26.11 — прогон 2 (runs/20261126T134556Z-conflicts, коммит 9c0686e, бюджет 300 по умолчанию, промпт строже)

12. **Метрики:** 12 733 пары → 1322 после фильтра → 299 вызовов, 0 сбоев, 282 933 / 49 917 токенов (946 / 167 на вызов), 249 с LLM, 267 с всего. Находки: contradiction 4, possible 1, dept_difference 47, отброшено 1.

Компромисс точность/полнота записан для владельца: прогон 1 — 5/7 ориентиров и 5 ложных из 13; прогон 2 — 0 ложных, но 2/7.
15. **Масштаб (300 документов, по замерам):** ≈ 53 тыс. окон, ≈ 955 тыс. пар-кандидатов, ≈ 99 тыс. после фильтра. Без бюджета: 99 тыс. вызовов × (946 вход + 167 выход) ≈ 94 млн / 17 млн токенов, ≈ 23 ч на стенде при 4 потоках (1.2 вызова/с). Не перепроверены на стенде: приём цитат с «...». Различия дирекций (47) вручную не размечал.

## 26.11 — ночной режим «точность выше стоимости» (решение владельца)

17. **Задание:** запуск ночью/по расписанию, вызовы не ограничены; цель — полнота ≥ 5/7 при ложных ≈ 0.
18. **Полнота отбора:** ночью нет бюджета и лимита на окно; фильтр шире (sim_min 0.06→0, condition_vs_rule при близости ≥ 0.15 вместо 0.25, близость без сигнала ≥ 0.4), блок по действию до 25 партнёров. Локально без эмбеддингов: 1001 пара к судье, все 7 ориентиров (включая K1 7.4↔9.2, K7 2.18↔4.1, K4 22.3↔24.3) доходят до судьи. Отбросил «полный перебор внутри документа»: на корпусе возможно, но для 300 документов не масштабируется, а ориентиры уже проходят.
19. **Точность — два этапа.** Этап 1 — мягкий судья (промпт прогона 1, без списка «не противоречие»: давал 5/7). Этап 2 — каждая contradiction/possible перепроверяется тремя независимыми вызовами: ревизор (A→B), ревизор с обратным порядком (B→A — модель склонна к первому пункту), «адвокат регламента» (сначала защищает: почему это НЕ противоречие, и отмечает, держится ли защита на тексте). Итог: ≥ 2 из 3 за несовместимость → находка выжила; contradiction, если так считают ≥ 2, иначе possible; уверенность = доля голосов за итог. Ревизорам: «текст сам не объясняет совместимость → possible, не none» (в прогоне 2 строгий судья терял K5 из-за «сомневаешься — none»). Не выжившее — раздел «Отклонено перепроверкой» с доводами каждого судьи. Перепроверка не видит объяснения этапа 1 (независимость). Отбросил: перепроверку dept_difference/dependency (это не дефекты), пятиголосие (×5 вызовов, а разногласия трёх уже видны).
20. **Инкрементальный режим:** `changed=<префикс doc_id>` или `prev=<metrics.json прошлого прогона>` (в metrics теперь `doc_ids`; doc_id = sha256 файла, значит изменённый файл = новый doc_id). Пустой список изменений → 0 пар (а не весь корпус — поймал и исправил).
21. **Расписание:** описано в README и в шапке задачи раннера (crontab на машине раннера вызывает `submit.py conflicts`); на стенде ничего не ставил.
