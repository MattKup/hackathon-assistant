# Помощник по регламентам: от загрузки документа до ответа, которому можно верить, и базы знаний, которая растёт сама

**Хакатон «ИИКузница» 26–28.11.2026, задача «Поиск ответов по корпоративным документам». Автор: Марат Якупов.**

Я сделал помощника, который закрывает весь путь знания в компании. Владелец регламента загружает документ любого общепринятого формата, и помощник сам приводит его к нужным пунктам. Сотрудник спрашивает своими словами, с опечатками и жаргоном, а помощник отвечает **строго по действующему регламенту**: по шагам, со ссылкой на пункт и дословной цитатой, которую сверяет программа, а не модель. Если ответ зависит от ситуации, помощник уточняет (кейс 2). Если ответа в регламентах нет, он не додумывает, а передаёт вопрос в Службу качества с готовым черновиком (кейс 1). Ответ эксперта становится карточкой знания, и тот же вопрос, заданный другими словами, дальше закрывается сразу, без нового письма (кейс 3). Ночью, в период наименьшей нагрузки, запускается модуль поиска противоречий в документах, и его находки становятся задачами на изменение или дополнение регламента. Всё работает на одном сервере с потребительской видеокартой RTX 5090, на открытых моделях: документы и вопросы наружу не уходят.

<a id="roles"></a>
## Сценарий по ролям

**Сотрудник.** Менеджер готовит конкурс и пишет в чат: «за сколько запускать заявку на расчёт?». Помощник видит, что в трёх дирекциях сроки разные, и спрашивает, какая дирекция ведёт проект. Варианты даны кнопками, есть «Проект нескольких дирекций» и «Не знаю». Менеджер выбирает «Техническая дирекция» и за секунды получает ответ: что сделать, кто отвечает, в какой срок, со ссылкой на пункт 1.5. Нажимает на ссылку, и справа открывается текст пункта с выделенной цитатой. Пишет «а по ДБРЦТ?» и сразу получает ответ для другой дирекции, без повторного поиска.

**Сотрудник, у которого нестандартный вопрос.** «Какое обучение должен пройти новый руководитель проекта?» В регламентах этого нет. Помощник не сочиняет, а пишет: «Вопрос передан в Службу качества, обращение №…, ответ придёт на почту, вы в копии».

**Эксперт Службы качества.** Получает письмо, где уже есть вопрос, диалог с сотрудником, близкие пункты регламентов и черновик ответа. Отвечает прямо на письмо. Промежуточное «уточняю у коллег» сотруднику не публикуется, итоговый ответ становится карточкой знания. Эксперт правит формулировку, отмечает, для каких дирекций она действует, и решает, оставить её в базе ответов или закрепить в регламенте. Через день другой сотрудник спрашивает то же другими словами, и помощник отвечает по карточке. Письма эксперту уже нет.

**Руководитель Службы качества.** Видит, какие вопросы задают чаще всего, чего нет в регламентах и какой вопрос пришёл в пятый раз за неделю: о повторах приходит сигнал письмом. Утром разбирает кандидатов в противоречия, которые ночью нашёл анализатор, и получает единый реестр задач на изменение регламента.

**Владелец регламента или администратор.** Загружает новый регламент в любом привычном виде: Word, PDF, скан, Excel, страница Confluence и другие. Выбирает подразделение из списка или вписывает новое. Через минуту документ в реестре, его можно открыть целиком и искать внутри, а помощник уже отвечает по нему. Программист для этого не нужен.

<a id="cases"></a>
## Три кейса задачи

| Кейс | Как я его решил |
| --- | --- |
| **1. Ответ строго по регламенту; нет ответа, значит в Службу качества** | Ответ по каждой дирекции с пунктом и дословной выдержкой. Цитаты, числа, роли и «можно / нельзя» сверяются с текстом пункта **кодом**: шаг без опоры отбрасывается. Если опоры нет, уходит письмо в Службу качества с черновиком для эксперта, сотрудник в копии и видит номер обращения. |
| **2. Уточняющий диалог** | Если ответы дирекций различаются, а дирекция не названа, помощник спрашивает её кнопками («Не знаю» даёт ответ по всем). Если ответ зависит от условия из пункта, задаёт один вопрос словами этого пункта, например есть ли гарантийное письмо. На размытый вопрос предлагает близкие темы из регламентов. Ответы по всем дирекциям готовятся заранее, поэтому выбор показывается мгновенно. |
| **3. Дообучение через Службу качества** | Итоговый ответ эксперта → карточка знания → подтверждение → повторный вопрос другими словами отвечается по карточке. **Регламент главнее карточки:** если карточка расходится с действующим пунктом, сотрудник получает однозначный ответ по регламенту, а расхождение попадает в реестр изменений. |

<a id="quality"></a>
## Что получает Служба качества

- **Эксперт не разбирает один вопрос дважды.** Повтор закрывается карточкой знания.
- **У эксперта готовый контекст и черновик.** Вопрос, диалог, близкие пункты и вариант ответа приходят прямо в письме.
- **Видно, что разбирать в первую очередь.** Мониторинг повторов «задавали N раз за период» присылает сигнал письмом.
- **Видно, где регламент неполон.** Аналитика вопросов без ответа и журнал запросов.
- **Противоречия находятся заранее.** Их ищет ночной анализатор, решение за экспертом.
- **Один список задач для владельца регламента.** Реестр изменений: закрепить ответ, устранить противоречие, снять расхождение.
- **Настройки без программиста.** Темы, которые Служба качества разбирает вне регламентов, советы «Обратите внимание», период и порог повторов меняются в интерфейсе и действуют сразу. Помощник работает и без них: любой вопрос об общих правилах работы в компании и так уходит в Службу качества, а список тем лишь помогает в пограничных случаях (на 30 вопросах вне регламентов со списком все 30 разобраны верно, без него 27). Советы «Обратите внимание» и подключённые внешние источники видны там же, источник открывается целиком.

<a id="path"></a>
## Путь знания: от загрузки до дообучения

```
документ (Word, PDF, скан, Excel, Confluence…)
   └─► doc-intel: распознавание и структура ─► нормализатор: пункты, разделы, путь раздела ─► индекс (слова + смысл)
вопрос сотрудника
   └─► разбор вопроса (термины регламента, сокращения, дирекции, тип вопроса)
   └─► поиск: BM25 + bge-m3 → объединение → реранкер bge-reranker-v2-m3 (сначала по всей базе, затем вглубь в лучших документах)
   └─► ответ по каждой дирекции параллельно, с дословными цитатами ─► второй проход для слабых ответов (добор пунктов по ссылкам)
   └─► проверки кодом: цитата, числа, роли, запрет ↔ разрешение, опора каждой фразы
   └─► решение: ответ / уточнение / противоречие / письмо в Службу качества / «вне регламентов»
   └─► «Обратите внимание»: советы Службы качества и внешние источники, отдельно от ответа
ответ эксперта ─► карточка знания ─► подтверждение ─► ответы по карточке ─► реестр изменений регламента
ночью ─► анализатор противоречий ─► кандидаты ─► решение эксперта ─► учитываются в ответах
```

<a id="modules"></a>
## Модули

**Приём документов: платформа doc-intel.** Подключил собственную платформу обработки документов, чтобы помощник принимал реальные документы компании, а не только аккуратный Word. Она понимает более 20 форматов: PDF и сканы, фото с телефона, многостраничные TIFF, DOC/DOCX, XLS/XLSX/CSV, PPT/PPTX, ODT, RTF, HTML, Markdown, письма EML, выгрузки чатов и ZIP-архивы целиком. Скан или фото выравнивается, поворот листа определяется по форме букв. На длинных деловых документах точность распознавания 99,2–99,4 % символов, числа, даты и номера без ошибок. Платформа восстанавливает автонумерацию пунктов Word, сохраняет таблицы и путь раздела. Скрытый текст (белый, микроскопический, за краем страницы) в поиск не попадает, фразы-команды для ИИ («игнорируй предыдущие указания») помечаются как риск, тип файла проверяется по содержимому, ZIP-бомбы отсекаются. Распознаёт открытая модель LightOnOCR-2-1B, около 1 млрд параметров: я выбрал её из более чем 20 открытых моделей, понимающих русский, потому что маленькая модель быстро работает на обычной видеокарте. Сейчас распознавание на стенде тестово работает на одной RTX 3090. В режиме, когда модель читает 16 страниц параллельно, это до 3 600 страниц сканов в час при той же точности; по одной странице 640 страниц в час и около 6 ₽ электричества на 1 000 страниц. Подключение по HTTP API: `app/ingest/upload.py`.

**Нормализатор документов.** Создал, чтобы помощник одинаково работал с любым источником, и все доработки под документы делал здесь, на этапе подготовки, а не в логике ответа. Любой документ (Word, распознанный PDF, страница Confluence, текстовый файл) при загрузке проходит нормализатор, и из него автоматически собирается всё, что нужно для ответа:

- нарезка по пунктам, а если пунктов нет, то по заголовкам или смысловым блокам; фрагменты по 600–1 000 знаков с полным путём раздела; вводная часть до первого пункта не теряется; списки и таблицы остаются внутри своего пункта;
- указатель пунктов и перекрёстных ссылок «п. X.Y»: по нему агент добирает пункты, на которые ссылается найденный текст;
- расшифровки сокращений из самого текста («SS (Менеджер по продаже решений)»): модель получает их вместе с фрагментами и не придумывает свои;
- сокращения документа, которых нет в словаре (например, ТЗТ): если сотрудник пишет такое сокращение, помощник ищет его как есть и не подменяет похожим;
- подразделение и этап берутся из описания рядом с документом, а не из кода.

Новый документ заказчика проходит тот же путь: после загрузки указатель, расшифровки и сокращения пересобираются сами. Код: `app/chunking`, `app/parsers`, `app/ingest`, `app/pipeline.py` (`build_index`, `doc_abbr`).

**Коннектор Confluence.** Добавил, потому что внутренняя база знаний у заказчика в Confluence без аддонов. Коннектор забирает страницы пространства (Cloud и Server/Data Center), обновляет только изменённые по версии страницы и передаёт их нормализатору. Проверен на записанных ответах API. Код: `app/connectors/confluence.py`.

**Реестр документов и подразделений.** Подразделения, названия, синонимы и маршруты «вне регламентов» вынесены в конфигурацию: новое подразделение подключается загрузкой документа, без правки кода. В интерфейсе есть реестр с поиском и просмотром документа целиком. Код: `config/documents.json`, `app/registry`.

**Разбор вопроса.** Модель переводит разговорное на язык регламента («офер» → ТКП, «проджект» → руководитель проекта), определяет тип вопроса (вопрос, «где описано», «сделай за меня», вне регламентов) и названные дирекции. Сокращения из документов сохраняет как есть. Если помощник счёл вопрос не про регламенты, а сотрудник не согласен, кнопка «Передать в службу качества» отправляет вопрос эксперту одним нажатием. Код: `app/answer/understand.py`.

**Поиск.** Гибридный: по словам (BM25) и по смыслу (bge-m3), затем объединение и реранкер. Сначала ищет по всей базе, затем подробно только в лучших документах, поэтому число поисков и вызовов модели на вопрос одинаково на 4 и на 300 регламентах. Подробности ниже, код: `app/search`.

**Ответ с проверкой кодом.** Ответ готовится по каждой дирекции отдельно, по JSON-схеме, с дословными цитатами. Затем программа сверяет каждую цитату, число и роль с текстом пункта и отбрасывает то, что модель добавила от себя. Слабый ответ получает второй проход: агент добирает пункты по ссылкам «п. X.Y» и соседние. Код: `app/answer`, `app/pipeline.py`.

**Диалог.** Уточнение дирекции, условия и темы; режим «Сразу по всем дирекциям»; продолжения вида «а по ДБРЦТ?». Ответы по всем дирекциям готовятся сразу и хранятся в диалоге, поэтому выбор показывается без повторного расчёта. Код: `app/dialog`.

**Служба качества: обращения и база знаний.** Письмо эксперту с черновиком ответа (SMTP, в демо Mailpit), разбор ответа эксперта из почты, карточки знаний с подтверждением, выбор «база ответов» или «закрепить в регламенте», реестр изменений регламента. Код: `app/escalation`.

**Анализатор противоречий.** Создал, потому что регламенты пишут разные люди, и пункты расходятся между собой и между дирекциями, а сотрудник должен получить однозначный ответ. Анализатор перебирает не все пары, а кандидатов с общей темой и действием, и находит противоречия, различия дирекций и зависимости от условий. По каждой находке даёт дословные цитаты обоих пунктов (их сверяет код) и объяснение, после чего три независимых проверяющих перепроверяют находку. Решает человек: эксперт Службы качества подтверждает пару или отклоняет. Подтверждённая пара сразу учитывается в ответах. Сотрудник видит оба пункта и правило «пока регламент действует, поступать вопреки ему нельзя», а Служба качества получает задачу изменить регламент. Анализатор работает ночью, когда видеокарта свободна от вопросов сотрудников. При изменении документа заново проверяются только пары с его пунктами. Код: `app/analysis/conflicts.py`, `app/analysis/registry.py`, страница «Противоречия».

**«Обратите внимание: не из регламента».** Полный ответ состоит из ответа по регламенту и совета, на что ещё посмотреть в конкретном случае: Гражданский кодекс, лицензируемые виды деятельности, особые виды заказчиков. Информация из регламентов наружу не уходит, а советы берутся только из того, что задала Служба качества: правила «слова-признаки → совет» в веб-«Настройках» и внешние документы (закон, справка), загруженные в «Документах» с типом «Внешний источник». Блок показывается под ответом отдельно и с пометкой «не из регламента». Модель его не пишет, а внешние документы не участвуют в ответе по регламенту. При желании сюда подключается внешний API, например правовая база. Код: `app/answer/aspects.py`.

Пример. Сотрудник спрашивает: «Можно ли заложить в бюджет проекта подарок клиенту за 10 000 ₽?» По регламенту ответ «нет»: бюджет проекта нельзя тратить на подарки клиентам (ТД п. 13.6, ИБ п. 7.9.6). Под ответом помощник добавляет: «Обратите внимание, не из регламента: подарок другой компании дороже 3 000 ₽ не допускается Гражданским кодексом (ст. 575), из какого бюджета его ни оплачивай». Совет взят из правила Службы качества и из загруженной выдержки статьи (`docs/examples/`). Так же устроен пример с брифинга про такси в командировке, выпавшей на выходной. Регламенты об этом молчат, вопрос уходит в Службу качества, а под ответом стоит совет оформить работу в выходной приказом, иначе расходы могут не признать обоснованными.

**Аналитика и мониторинг повторов.** Что спрашивают, как отвечает помощник, чего нет в регламентах, журнал запросов. Повторяющиеся вопросы, в том числе заданные другими словами, считаются, и при достижении порога Служба качества получает сигнал. Код: `app/escalation/repeats.py`, страница «Аналитика».

**Быстрый ответ и кэш.** Вопрос, который уже задавали теми же словами, отвечается сразу, около 0 с, без поиска и модели: помощник отдаёт уже проверенный ответ. После перезапуска последние вопросы из журнала прогреваются заранее. Ответы по отдельным дирекциям тоже кэшируются. Всё это сбрасывается при загрузке документа, новой карточке знания, решении по противоречию и изменении настроек Службы качества, поэтому устаревший ответ не выдаётся. Письма в Службу качества и уточнения условий всегда готовятся заново. Пока новый ответ готовится, на экране видно, что помощник делает сейчас: какой пункт нашёл, по какой дирекции пишет ответ, что сверяет. Код: `app/answer/cache.py`, `app/api/server.py`.

**Проверка качества.** Прогон наборов вопросов, воронка «поиск → контекст → цитата → исход», парное сравнение версий, замер энергии на вопрос. Каждое изменение я включал, только если независимый судья подтверждал, что оно не добавляет ошибок. Код: `scripts/eval`, `scripts/stand`.

<a id="search"></a>
## Как устроен поиск

Поиск идёт без модели, по готовым фрагментам, которые подготовил нормализатор. У каждого фрагмента есть полный путь «Документ › Раздел N «Заголовок» › п. N.M», и этот путь участвует в поиске вместе с текстом. Поэтому вопрос, слова которого есть только в названии раздела, всё равно находит пункт.

1. **По словам: BM25.** Основы слов (свой стеммер для русского, стоп-слова), параметры k1 = 1,4, b = 0,6. Ловит точные термины, номера и сокращения: «ЗнП», «ТКП», «12 рабочих часов». Берёт 40 лучших фрагментов.
2. **По смыслу: bge-m3.** Вектор вопроса сравнивается с векторами фрагментов. Так находится пункт, сказанный другими словами: «когда клиент торопит» → «сроки подачи заявки». Тоже 40 лучших. Векторы фрагментов посчитаны один раз и хранятся на диске.
3. **Объединение: RRF.** Каждый фрагмент получает 1 / (60 + место) из каждого списка, баллы складываются. Так два разных по природе поиска объединяются без подбора весов, а фрагмент, высоко стоящий в обоих, поднимается наверх.
4. **Реранкер: bge-reranker-v2-m3.** 16 финалистов заново оцениваются парой «вопрос и путь раздела с текстом фрагмента». Это самый точный, но и самый дорогой шаг, поэтому он работает только по финалистам.
5. **Несколько формулировок.** Ищется исходный вопрос сотрудника и до трёх формулировок «словами регламента», которые подготовил разбор вопроса. Исходная формулировка в поиске всегда: переписывание может увести в сторону.
6. **В два шага.** Сначала один поиск по всей базе показывает, в каких документах ответ. Затем идёт подробный поиск только в лучших: не больше 3 дирекций по 3 документа. Поэтому число поисков и вызовов модели одинаково на 4 и на 300 регламентах.
7. **Если что-то недоступно,** поиск не падает: без эмбеддингов работает BM25, без реранкера используется порядок RRF.

Где теряется точность, я мерил по шагам. На трудных вопросах нужный пункт попадает в контекст модели в 90 % случаев, а в ответе используется в 64 %. Значит, главный резерв не в поиске, а в том, как модель использует найденное. Поэтому основная работа шла в проверках кодом и агентных проходах.

<a id="checks"></a>
## Как код проверяет ответ модели

Модель возвращает ответ по жёсткой JSON-схеме: вердикт (ответ, ответ с оговоркой, противоречие или нет ответа), краткий ответ и до 7 шагов, у каждого шага есть «что сделать», «кто», «срок», номер фрагмента и дословная цитата. Сам по себе структурированный вывод является общей практикой. Моё в том, что каждый шаг обязан подтвердить себя цитатой, и до сотрудника доходит только то, что прошло проверки кодом:

| Проверка | Что делает | Зачем |
| --- | --- | --- |
| Цитата | Цитата шага должна дословно быть в тексте фрагмента, на который шаг ссылается. Допускаются пропущенные маркеры списка и сокращение многоточием, если каждый кусок дословный и стоит в том же порядке. Почти дословная цитата (≥ 80 % слов) заменяется точным предложением пункта | Ссылка на пункт всегда настоящая, выделенная цитата в интерфейсе взята из текста |
| Числа | Каждое число в шаге (срок, сумма, процент) должно быть в тексте пункта | «3 рабочих дня» не превращаются в «5» |
| Роли | Роль в шаге («Руководитель проекта», «SS») должна быть в пункте, с учётом расшифровок из словаря и из текста документов | Правило одной роли не приписывается другой |
| Добавлено из вопроса | Шаг, в котором есть слова из вопроса, но нет опоры в пункте, отбрасывается | Модель не «додумывает» ситуацию сотрудника |
| Запрет и разрешение | Если краткий ответ разрешает, а в пункте есть запрет на тот же случай, ответ становится «с оговоркой» и показывает запрет дословно | «Можно» никогда не перекрывает «нельзя» |
| Опора краткого ответа | Фраза краткого ответа без общих слов с процитированными пунктами убирается | Краткий ответ не говорит больше, чем шаги |
| Всё отброшено | Если не осталось ни одного подтверждённого шага, вердикт становится «нет ответа» | Лучше письмо в Службу качества, чем ответ без опоры |

Каждое срабатывание видно в «Как найден ответ», например «1 утверждение отброшено проверкой цитат». Замер на 100 корпоративных вопросах: из 189 шагов модели проверки отбросили 5.

## Стоимость эксплуатации

**Затраты: электричество одного сервера.** Модели открытые и работают на своей видеокарте, поэтому цена токенов равна нулю. Я замерил потребление видеокарты на 80 вопросах подряд (мощность раз в секунду): под нагрузкой в среднем 474 Вт, в простое 81 Вт, **0,94 Вт·ч на вопрос ≈ 0,0075 ₽** при тарифе 8 ₽/кВт·ч.

| Шаг агента | Когда | Вызовов на вопрос | Токены вход / выход | ₽ электричества (8 ₽/кВт·ч) | ₽ у облачного провайдера, для сравнения |
| --- | --- | --- | --- | --- | --- |
| Разбор вопроса | Всегда | 1 | 1 147 / 100 | 0,0010 | 0,07 |
| Ответ по дирекции с цитатами, вкл. второй проход | По каждой дирекции, где есть опора | 1,77 | 4 060 / 288 | 0,0064 | 0,42 |
| Сравнение дирекций, проверка темы | Перед уточнением, на границе темы | 0,35 | 443 / 49 | 0,0001 | 0,01 |
| Поиск: эмбеддинги + реранкер | Всегда | 12 поисков | 2 954 / нет | Входит в замер | 0,03 |
| Черновик для эксперта | Только при письме в Службу качества | +1 | Нет данных | Нет данных | Нет данных |
| **Итого на вопрос** |  | ≈ 3 вызова модели |  | **≈ 0,0075** | **≈ 0,53** |

Токены замерены на 211 вопросах всех типов. Электричество замерено на вопрос целиком и распределено по шагам пропорционально токенам модели. Облако для сравнения: та же модель Qwen3.8-27B у официального провайдера (Alibaba Model Studio, $0,5 / $3 за 1 млн токенов, курс ЦБ 82,313 ₽/$, без НДС). Расчёт с формулами лежит в [docs/economics.xlsx](docs/economics.xlsx).

- **Нагрузка заказчика.** 100–120 вопросов в день → около 20 ₽ в месяц на ответы. Простой видеокарты круглосуточно добавляет около 470 ₽ в месяц, и ночью это время забирает проверка регламентов. Остальной сервер (процессор, память) в замер не входит.
- **Цена вопроса зависит от вопроса.** Вопрос по одной дирекции дешевле, вопрос по нескольким дороже: ответ готовится по каждой.
- **Цена и скорость вопроса одинаковы на 4 и на 300 регламентах.** Поиск сначала отбирает лучшие документы по всей базе и подробно ищет только в них, поэтому на любой базе модель вызывается одинаковое число раз. Проверено на базе в 75 раз больше: столько же поисков и вызовов модели.
- **С базой растут только разовые затраты:** распознавание документа при загрузке и время ночной проверки противоречий, которая идёт инкрементально, по изменённым документам.
- **Экономия времени экспертов.** Повторный вопрос закрывается карточкой знания, и эксперт на него время не тратит. Мониторинг повторов показывает, где эта экономия.
- **Оборудование.** Один сервер с потребительской видеокартой RTX 5090 32 ГБ, не серверный ускоритель.

<a id="stack"></a>
## Стек, модели и лицензии

Всё работает локально, внешних API нет.

| Роль | Компонент | Лицензия |
| --- | --- | --- |
| Ответы, разбор вопроса, черновик для эксперта | Qwen3.8-27B AWQ INT4 (база Qwen/Qwen3.8-27B), vLLM 0.28.0 | Apache-2.0 |
| Эмбеддинги | BAAI/bge-m3, TEI | MIT |
| Реранкер | BAAI/bge-reranker-v2-m3, TEI | Apache-2.0 |
| Распознавание сканов | LightOnOCR-2-1B внутри doc-intel | Apache-2.0 |
| Приём и разбор документов | doc-intel, моя платформа, создана до хакатона, подключается по HTTP API | Собственная, закрытая; в репозиторий не входит |
| Почта Службы качества в демо | Mailpit | MIT |
| Код помощника | Python 3.12, numpy, SQLite, веб-интерфейс без фреймворков | MIT (LICENSE) |

Железо стенда: одна RTX 5090 32 ГБ, на ней модель ответа, эмбеддинги и реранкер. Распознавание сканов идёт на втором узле с RTX 3090.

**Где предел модели.** Чтобы модель на 27 млрд параметров поместилась на одну видеокарту 32 ГБ вместе с поиском, она работает в 4-битном сжатии (AWQ INT4). Я проверил, сколько она способна выжать при идеальном поиске: подставил ей заведомо нужный пункт. На трудных вопросах верных действий стало 106 из 150 вместо 99, а нужный пункт модель использует в 72 % случаев. Это потолок самой модели, а не поиска. Он совпадает с выводами исследования Google о «достаточном контексте» ([Sufficient Context, arXiv:2411.06037](https://arxiv.org/abs/2411.06037)): даже когда в контексте есть всё нужное, модели этого класса отвечают верно примерно в 7 случаях из 10. Поэтому следующий шаг по точности упирается в модель: крупнее или в 8 битах, что требует видеокарты с большей памятью или второй карты (см. «Что дальше»).

Эта проверка, как и все остальные, сделана на потребительской RTX 5090 с моделью в 4 битах. На H200 та же модель помещается без сжатия и, по расчёту, отвечает примерно с той же скоростью, что сейчас на 5090. Замера точности без сжатия у нас нет: это первый шаг после хакатона.

<a id="run"></a>
## Запуск и поставка

```
# демо без моделей (BM25 + заглушка модели): интерфейс и сценарии
python3 -m app.api.server --corpus <папка с регламентами> --data data/app --mock --port 8080

# стенд: помощник + Mailpit
cd deploy && docker compose up -d
```

- `deploy/compose.yaml` поднимает помощника и Mailpit. Сервисы моделей запускаются отдельно и задаются переменными окружения: `LLM_BASE_URL` (OpenAI-совместимый vLLM; на стенде kv-кэш fp8, контекст 16 384, prefix caching, без рассуждения), `TEI_EMBED_URL`, `TEI_RERANK_URL`, `DOC_INTEL_URL`. Наружу сервисы не слушают, вход через обратный прокси с паролем.
- После перезапуска видеокарты эмбеддинги поднимаются раньше vLLM: их прогрев требует свободной памяти.
- Подключение компании делается конфигурацией, а не кодом: подразделения и документы (`config/documents.json`), адрес почты Службы качества (`QA_EMAIL`, SMTP), темы, советы и мониторинг повторов (веб «Настройки»).
- Анализатор противоречий: `scripts/stand/conflicts.sh <корпус>`; инкрементально с `prev=<metrics.json прошлого прогона>`; по расписанию строкой crontab в часы наименьшей нагрузки; кандидаты в реестр через `POST /api/conflicts/import`.
- Тесты: `python3 -m unittest discover -s tests`.

<a id="next"></a>
## Что дальше

Основа для каждого шага уже есть в продукте, дальше её расширение.

- **Модуль интеграций: новые источники знаний без изменения логики ответа.** Уже работают doc-intel (20+ форматов), коннектор Confluence и внешние источники для блока «Обратите внимание». Следующие коннекторы: справочники компании, разделы частых вопросов, правовые базы по API (КонсультантПлюс, Гарант), инструменты компании по MCP. Дальний горизонт: действия по ответу, например завести заявку или отправить на согласование.
- **Внешние источники без утечки.** Наружу уходит только обезличенный общий вопрос, а ответ соединяется с регламентом на своём сервере. Обезличивание я уже отработал: модуль защиты идентификаторов перед отправкой данных во внешние модели работает в другом моём продукте. Разбор вопроса здесь уже переформулирует вопрос словами регламента, и это первый шаг такого посредника.
- **Модель крупнее.** Сейчас модель ответа работает в 4 битах, чтобы уместиться на одной видеокарте 32 ГБ вместе с поиском. Модель крупнее или в 8 битах на карте с большей памятью может поднять потолок точности, который упирается именно в модель (см. «Где предел модели»).
- **Ответ по нескольким дирекциям без пропусков.** Главный источник ошибок на трудных вопросах: потерянная дирекция или исключение. Дальше нужно выбирать дополнительные пункты кодом, а не моделью: вариант с моделью («Учтите также») я проверил и не включил, он давал ошибки в верных ответах. Опция «Связанные пункты» уже есть в чате.
- **Несколько вопросов в одном сообщении:** разбор на части и ответ по каждой.
- **Быстрый ответ на новый вопрос:** сначала короткий ответ по лучшему пункту, полная проверка и второй проход в фоне. Сейчас мгновенно отвечается только повторный вопрос.
- **Ночная подготовка знаний для большой базы:** заранее подготовить к каждому пункту вопросы, как их зададут сотрудники; кандидатов анализатора, отклонённых перепроверкой, отдавать на решение эксперта, а не выбрасывать.
