# Помощник по регламентам: от загрузки документа до ответа, которому можно верить, и базы знаний, которая растёт сама

**Хакатон «ИИКузница» 26–28.11.2026, задача «Поиск ответов по корпоративным документам». Автор — Марат Якупов.**

Я сделал помощника, который закрывает весь путь знания в компании. Владелец регламента загружает документ любого формата — помощник сам приводит его к пунктам. Сотрудник спрашивает своими словами, с опечатками и жаргоном — помощник отвечает **строго по действующему регламенту**: по шагам, со ссылкой на пункт и дословной цитатой, которую сверяет программа, а не модель. Если ответ зависит от ситуации — уточняет (кейс 2). Если ответа в регламентах нет — не додумывает, а передаёт вопрос в Службу качества с готовым черновиком (кейс 1). Ответ эксперта становится карточкой знания, и тот же вопрос, заданный другими словами, дальше закрывается сразу, без нового письма (кейс 3). Противоречия в регламентах находятся ночью и становятся задачами на изменение регламента. Всё работает на одном сервере с потребительской видеокартой, на открытых моделях: документы и вопросы наружу не уходят.

<a id="roles"></a>
## Сценарий по ролям

**Сотрудник.** Менеджер готовит конкурс и пишет в чат: «за сколько запускать заявку на расчёт?». Помощник видит, что в трёх дирекциях сроки разные, и спрашивает: «Какая дирекция ведёт проект?» — кнопками, с вариантами «Проект нескольких дирекций» и «Не знаю». Менеджер выбирает «Техническая дирекция» и за секунду получает ответ: что сделать, кто отвечает, в какой срок, со ссылкой на пункт 1.5. Нажимает на ссылку — справа открывается текст пункта с выделенной цитатой. Пишет «а по ДБРЦТ?» — получает ответ для другой дирекции сразу, без повторного поиска.

**Сотрудник, у которого нестандартный вопрос.** «Какое обучение должен пройти новый руководитель проекта?» — в регламентах этого нет. Помощник не сочиняет, а пишет: «Вопрос передан в Службу качества, обращение №…, ответ придёт на почту, вы в копии».

**Эксперт Службы качества.** Получает письмо, где уже есть вопрос, диалог с сотрудником, близкие пункты регламентов и черновик ответа. Отвечает прямо на письмо. Промежуточное «уточняю у коллег» сотруднику не публикуется, итоговый ответ становится карточкой знания. Эксперт правит формулировку, отмечает, для каких дирекций она действует, и решает: оставить в базе ответов или закрепить в регламенте. Через день другой сотрудник спрашивает то же другими словами — помощник отвечает по карточке, письма эксперту уже нет.

**Руководитель Службы качества.** Видит, какие вопросы задают чаще всего, чего нет в регламентах и какой вопрос пришёл в пятый раз за неделю (о повторах приходит сигнал письмом). Утром разбирает кандидатов в противоречия, которые ночью нашёл анализатор, и получает единый реестр задач на изменение регламента.

**Владелец регламента или администратор.** Загружает новый регламент — Word, PDF, скан, Excel, страницу Confluence — и выбирает подразделение из списка или вписывает новое. Через минуту документ в реестре, его можно открыть целиком и искать внутри, а помощник уже отвечает по нему. Программист не нужен.

<a id="cases"></a>
## Три кейса задачи

| Кейс | Как я его решил |
|---|---|
| **1. Ответ строго по регламенту; нет ответа — в Службу качества** | Ответ по каждой дирекции с пунктом и дословной выдержкой. Цитаты, числа, роли и «можно / нельзя» сверяются с текстом пункта **кодом**: шаг без опоры отбрасывается. Нет опоры — письмо в Службу качества с черновиком для эксперта, сотрудник в копии и видит номер обращения. |
| **2. Уточняющий диалог** | Ответы дирекций различаются, а дирекция не названа — вопрос с кнопками («Не знаю» — ответ по всем). Ответ зависит от условия из пункта — один вопрос словами этого пункта (например, есть ли гарантийное письмо). Размытый вопрос — близкие темы из регламентов. Ответы по всем дирекциям готовятся заранее, поэтому выбор показывается мгновенно. |
| **3. Дообучение через Службу качества** | Итоговый ответ эксперта → карточка знания → подтверждение → повторный вопрос другими словами отвечается по карточке. **Регламент главнее карточки:** если карточка расходится с действующим пунктом, сотрудник получает однозначный ответ по регламенту, а расхождение попадает в реестр изменений. |

<a id="quality"></a>
## Что получает Служба качества

- **Эксперт не разбирает один вопрос дважды** — повтор закрывается карточкой знания.
- **У эксперта готовый контекст и черновик** — вопрос, диалог, близкие пункты, вариант ответа прямо в письме.
- **Видно, что разбирать в первую очередь** — мониторинг повторов «задавали N раз за период» с сигналом письмом.
- **Видно, где регламент неполон** — аналитика вопросов без ответа и журнал запросов.
- **Противоречия находятся заранее** — ночной анализатор, решение за экспертом.
- **Один список задач для владельца регламента** — реестр изменений: закрепить ответ, устранить противоречие, снять расхождение.
- **Настройки без программиста** — темы, которые Служба качества разбирает вне регламентов, период и порог повторов меняются в интерфейсе и действуют сразу.

<a id="path"></a>
## Путь знания: от загрузки до дообучения

```
документ (Word, PDF, скан, Excel, Confluence…)
   └─► doc-intel: распознавание и структура ─► нормализатор: пункты, разделы, путь раздела ─► индекс (слова + смысл)
вопрос сотрудника
   └─► разбор вопроса (термины регламента, сокращения, дирекции, тип вопроса)
   └─► поиск: BM25 + bge-m3 → объединение → реранкер bge-reranker-v2-m3 (сначала по всей базе, затем вглубь в лучших документах)
   └─► ответ по каждой дирекции параллельно, с дословными цитатами ─► второй проход для слабых ответов (добор пунктов по ссылкам)
   └─► проверки кодом: цитата, числа, роли, запрет ↔ разрешение, опора каждой фразы
   └─► решение: ответ / уточнение / противоречие / письмо в Службу качества / «вне регламентов»
ответ эксперта ─► карточка знания ─► подтверждение ─► ответы по карточке ─► реестр изменений регламента
ночью ─► анализатор противоречий ─► кандидаты ─► решение эксперта ─► учитываются в ответах
```

<a id="modules"></a>
## Модули

**Приём документов — платформа doc-intel.** Подключил собственную платформу обработки документов, чтобы помощник принимал реальные документы компании, а не только аккуратный Word. Она распознаёт сканы и фото (точность на длинных деловых документах — 99,2–99,4 % символов, числа и даты без ошибок), восстанавливает автонумерацию пунктов Word, сохраняет таблицы и путь раздела, отсекает скрытый текст и фразы-команды для ИИ. Более 20 форматов: PDF и сканы, DOC/DOCX, XLS/XLSX/CSV, PPT/PPTX, ODT, RTF, HTML, Markdown, EML. Модель распознавания — открытая LightOnOCR-2-1B, до 2,3 страницы в секунду. Подключение — `app/ingest/upload.py` (HTTP API).

**Нормализатор документов.** Создал, чтобы помощник одинаково работал с любым источником, и все доработки под документы делаю здесь, на этапе подготовки, а не в логике ответа. Любой документ — Word, распознанный PDF, страница Confluence, текстовый файл — при загрузке проходит нормализатор, и из него автоматически собирается всё, что нужно для ответа:
- нарезка по пунктам, а если пунктов нет — по заголовкам или смысловым блокам; фрагменты по 600–1 000 знаков с полным путём раздела; вводная часть до первого пункта не теряется; списки и таблицы остаются внутри своего пункта;
- указатель пунктов и перекрёстных ссылок «п. X.Y» — по нему агент добирает пункты, на которые ссылается найденный текст;
- расшифровки сокращений из самого текста («SS (Менеджер по продаже решений)») — модель получает их вместе с фрагментами и не придумывает свои;
- сокращения документа, которых нет в словаре (например, ТЗТ), — если сотрудник пишет такое сокращение, помощник ищет его как есть и не подменяет похожим;
- подразделение и этап — из описания рядом с документом, а не из кода.

Новый документ заказчика проходит тот же путь: после загрузки указатель, расшифровки и сокращения пересобираются сами. `app/chunking`, `app/parsers`, `app/ingest`, `app/pipeline.py` (`build_index`, `doc_abbr`).

**Коннектор Confluence.** Добавил, потому что у заказчика внутренняя база знаний — Confluence без аддонов. Забирает страницы пространства (Cloud и Server/Data Center), обновляет только изменённые по версии страницы и передаёт их нормализатору. Проверен на записанных ответах API. `app/connectors/confluence.py`.

**Реестр документов и подразделений.** Подразделения, названия, синонимы и маршруты «вне регламентов» вынесены в конфигурацию: новое подразделение подключается загрузкой документа, без правки кода. В интерфейсе — реестр с поиском и просмотром документа целиком. `config/documents.json`, `app/registry`.

**Разбор вопроса.** Модель переводит разговорное на язык регламента («офер» → ТКП, «проджект» → руководитель проекта), определяет тип вопроса (вопрос, «где описано», «сделай за меня», вне регламентов) и названные дирекции; сокращения из документов сохраняет как есть. `app/answer/understand.py`.

**Поиск.** Гибридный: по словам (BM25) и по смыслу (bge-m3), объединение и реранкер. Ищет сначала по всей базе, затем подробно только в лучших документах, поэтому число поисков и вызовов модели на вопрос одинаково на 4 и на 300 регламентах. `app/search`.

**Ответ с проверкой кодом.** Ответ готовится по каждой дирекции отдельно, по JSON-схеме, с дословными цитатами. Затем программа сверяет каждую цитату, число и роль с текстом пункта и отбрасывает то, что модель добавила от себя. Слабый ответ получает второй проход: агент добирает пункты по ссылкам «п. X.Y» и соседние. `app/answer`, `app/pipeline.py`.

**Диалог.** Уточнение дирекции, условия и темы; режим «Сразу по всем дирекциям»; продолжения вида «а по ДБРЦТ?». Ответы по всем дирекциям готовятся сразу и хранятся в диалоге — выбор показывается без повторного расчёта. `app/dialog`.

**Служба качества: обращения и база знаний.** Письмо эксперту с черновиком ответа (SMTP, в демо — Mailpit), разбор ответа эксперта из почты, карточки знаний с подтверждением, «база ответов» или «закрепить в регламенте», реестр изменений регламента. `app/escalation`.

**Анализатор противоречий.** Создал, потому что регламенты пишут разные люди, и пункты расходятся между собой и между дирекциями — а сотрудник должен получить однозначный ответ. Анализатор перебирает не все пары, а кандидатов по общей теме и действию, находит противоречия, различия дирекций и зависимости от условий. По каждой находке даёт дословные цитаты обоих пунктов (их сверяет код) и объяснение, а затем три независимых проверяющих перепроверяют находку. Решает человек: эксперт Службы качества подтверждает пару или отклоняет. Подтверждённая пара сразу учитывается в ответах — сотрудник видит оба пункта и правило «пока регламент действует, поступать вопреки ему нельзя», а Служба качества получает задачу изменить регламент. Работает ночью, когда видеокарта свободна от вопросов сотрудников; при изменении документа заново проверяются только пары с его пунктами. `app/analysis/conflicts.py`, `app/analysis/registry.py`, страница «Противоречия».

**Аналитика и мониторинг повторов.** Что спрашивают, как отвечает помощник, чего нет в регламентах, журнал запросов; повторяющиеся вопросы, в том числе другими словами, с сигналом Службе качества при достижении порога. `app/escalation/repeats.py`, страница «Аналитика».

**Кэш ответов.** Частый вопрос отвечается без вызова модели; кэш сбрасывается при загрузке документа или новой карточке знания, устаревший ответ не выдаётся. `app/answer/cache.py`.

**Проверка качества.** Прогон наборов вопросов, воронка «поиск → контекст → цитата → исход», парное сравнение версий, замер энергии на вопрос. Каждое изменение я включал, только если независимый судья подтверждал, что оно не добавляет ошибок. `scripts/eval`, `scripts/stand`.

<a id="search"></a>
## Как устроен поиск

Поиск идёт без модели, по готовым фрагментам, которые подготовил нормализатор. У каждого фрагмента есть полный путь «Документ › Раздел N «Заголовок» › п. N.M», и этот путь участвует в поиске вместе с текстом: вопрос, слова которого есть только в названии раздела, всё равно находит пункт.

1. **По словам — BM25.** Основы слов (свой стеммер для русского, стоп-слова), параметры k1 = 1,4, b = 0,6. Ловит точные термины, номера, сокращения: «ЗнП», «ТКП», «12 рабочих часов». Берёт 40 лучших фрагментов.
2. **По смыслу — bge-m3.** Вектор вопроса сравнивается с векторами фрагментов (косинус). Находит пункт, сказанный другими словами: «когда клиент торопит» → «сроки подачи заявки». Тоже 40 лучших. Векторы фрагментов посчитаны один раз и хранятся на диске.
3. **Объединение — RRF.** Каждый фрагмент получает 1 / (60 + место) из каждого списка, баллы складываются. Так два разных по природе поиска объединяются без подбора весов, а фрагмент, высоко стоящий в обоих, поднимается наверх.
4. **Реранкер — bge-reranker-v2-m3.** 16 финалистов заново оцениваются парой «вопрос — путь раздела + текст фрагмента». Это самый точный, но и самый дорогой шаг, поэтому он работает только по финалистам.
5. **Несколько формулировок.** Ищется исходный вопрос сотрудника и до трёх формулировок «словами регламента», которые подготовил разбор вопроса. Исходная всегда в поиске: переписывание может увести в сторону.
6. **В два шага.** Сначала один поиск по всей базе — он показывает, в каких документах ответ. Затем подробный поиск только в лучших: не больше 3 дирекций × 3 документов. Поэтому число поисков и вызовов модели одинаково на 4 и на 300 регламентах.
7. **Если что-то недоступно,** поиск не падает: без эмбеддингов работает BM25, без реранкера — порядок RRF.

Где теряется точность, я мерил по шагам. На трудных вопросах нужный пункт попадает в контекст модели в 90 % случаев, а в ответе используется в 64 %. Значит, главный резерв не в поиске, а в том, как модель использует найденное, — поэтому основная работа шла в проверках и агентных проходах ниже.

<a id="checks"></a>
## Как код проверяет ответ модели

Модель возвращает ответ по жёсткой JSON-схеме: вердикт (ответ / с оговоркой / противоречие / нет ответа), краткий ответ и до 7 шагов «что сделать — кто — срок — номер фрагмента — дословная цитата». Сам по себе структурированный вывод — общая практика. Моё в том, что каждый шаг обязан подтвердить себя цитатой, и до сотрудника доходит только то, что прошло проверки кодом:

| Проверка | Что делает | Зачем |
|---|---|---|
| Цитата | цитата шага должна дословно быть в тексте того фрагмента, на который шаг ссылается; допускаются пропущенные маркеры списка и сокращение многоточием, если каждый кусок дословный и стоит в том же порядке; почти дословная (≥ 80 % слов) заменяется точным предложением пункта | ссылка на пункт всегда настоящая, выделенная цитата в интерфейсе — из текста |
| Числа | каждое число в шаге (срок, сумма, процент) должно быть в тексте пункта | «3 рабочих дня» не превращается в «5» |
| Роли | роль в шаге («Руководитель проекта», «SS») должна быть в пункте — с учётом расшифровок из словаря и из текста документов | правило одной роли не приписывается другой |
| Добавлено из вопроса | шаг, в котором есть слова из вопроса, но нет опоры в пункте, отбрасывается | модель не «додумывает» ситуацию сотрудника |
| Запрет ↔ разрешение | если краткий ответ разрешает, а в пункте есть запрет на тот же случай, ответ становится «с оговоркой» и показывает запрет дословно | «можно» никогда не перекрывает «нельзя» |
| Опора краткого ответа | фраза краткого ответа без общих слов с процитированными пунктами убирается | краткий ответ не говорит больше, чем шаги |
| Всё отброшено | если не осталось ни одного подтверждённого шага, вердикт становится «нет ответа» | лучше письмо в Службу качества, чем ответ без опоры |

Каждое срабатывание видно в «Как найден ответ» («1 утверждение отброшено проверкой цитат»). Замер на 100 корпоративных вопросах: из 189 шагов модели проверки отбросили 10. Разбор этих 10 показал, что 5 были верными цитатами, сокращёнными многоточием, — проверка исправлена и теперь их принимает.

## Что я пробовал: гипотезы и результаты

Каждое изменение я включал выключателем, мерил на одних и тех же наборах вопросов и оставлял, только если независимый судья подтверждал пользу и не было новых ошибок.

| Гипотеза | Что сделал | Результат | Решение |
|---|---|---|---|
| Проверки кодом | цитата, числа, роли, «можно / нельзя», опора фраз | выдумок 12 → 5 на регрессии, 0 на простых вопросах | ✅ включено |
| Правила по разбору ошибок (Г1–Г7) | «вне регламентов» только без опоры; «не знаю дирекцию» → ответ по всем; формулировки словами регламента; названная дирекция — все её документы; фразы итога без опоры убираются | на трудных выдумок 8 → 4, критичных 2 → 1; точность в пределах шума | ✅ включено |
| Расшифровки из текста документов (Г12) | модель получает расшифровки сокращений из самих документов | 0 выдумок на простых; ушла выдуманная расшифровка роли; лучше базовой версии (p = 0,013) | ✅ включено |
| Рабочий вопрос вне регламентов → Служба качества | темы, которые разбирает Служба качества, — настройка | вне домена 22 → 30/30 | ✅ включено, настройка в вебе |
| «Прямого ответа не нашёл» | вместо утверждения «в регламенте об этом не сказано» | ложное «не сказано» было в 9 из 18 случаев | ✅ включено |
| Сокращения документа как есть | сокращение из вопроса, которое есть в документах (ТЗТ), не подменяется похожим словарным | простые вопросы без изменений, ошибка «ТЗТ → ФТТ» ушла | ✅ включено |
| Перекрёстный проход по дирекциям (Г17) | нашлось в одной дирекции — ищем то же правило в остальных | идёт замер | ⏳ по итогам замера |
| Дирекция только по указанию в вопросе (Г18) | модель не угадывает дирекцию по словам-ролям | идёт замер | ⏳ по итогам замера |
| Подсказка модели во втором проходе (Г8), диспетчер решения (Г9), рассуждение для отказов (Г10) | дополнительные шаги агента | в шуме; диспетчер ломал уточнение (18 → 1 из 29); рассуждение — до 149 с на вопрос | ❌ выключено |
| Рассуждение модели везде (Г11) | режим thinking для всех ответов | время × 5, сбои JSON, точность не выше | ❌ выключено |
| Словарь «слово сотрудника → термин» модели ответа (Г13) | подсказка сопоставления | в пределах шума | ❌ выключено |
| Вопросы-«входы» к пунктам, подготовленные ночью (Г14) | модель заранее пишет, как сотрудники спросят о пункте | 99 против 94 на трудных — шум (p = 0,36), +1 выдумка | ❌ сейчас; вернуться на большой базе |
| «Связанные пункты» (Г15) | код показывает соседний пункт с исключением | меток судьи не меняет; 25 из 30 подсказок лишние | ⚙️ опция в чате, выключена |
| «Учтите также» (Г16) | модель сама добавляет пункты к ответу | +2 / −5 по меткам судьи, 1 критичная ошибка | ❌ выключено |
| Перепроверка противоречий моделью как финальный фильтр | три модели-проверяющих решают, противоречие ли | модель «примиряет» пункты: оставила 2 из 7 известных | ❌ решает эксперт Службы качества |
| Исправление опечаток отдельным шагом модели | — | по литературе хуже, чем оставить исходный вопрос в поиске (QE-RAG) | ❌ не делал; исходный вопрос всегда в поиске |
| Карточка Службы качества главнее регламента | так сказали организаторы 26.11 | заказчик 27.11: регламент главнее, ответ однозначный | заменено: карточка дополняет, расхождение — в реестр изменений |

<a id="cost"></a>
## Стоимость эксплуатации

**Затраты — электричество одного сервера.** Модели открытые и работают на своей видеокарте, поэтому цена токенов — 0. Я замерил потребление видеокарты на 80 вопросах подряд (мощность раз в секунду): под нагрузкой в среднем 474 Вт, в простое 81 Вт, **0,94 Вт·ч на вопрос ≈ 0,0075 ₽** при тарифе 8 ₽/кВт·ч.

| Шаг агента | Когда | Вызовов на вопрос | Токены вход / выход | ₽ электричества (8 ₽/кВт·ч) | ₽ у облачного провайдера, для сравнения |
|---|---|---|---|---|---|
| Разбор вопроса | всегда | 1 | 1 147 / 100 | 0,0010 | 0,07 |
| Ответ по дирекции с цитатами, вкл. второй проход | по каждой дирекции, где есть опора | 1,77 | 4 060 / 288 | 0,0064 | 0,42 |
| Сравнение дирекций, проверка темы | перед уточнением, на границе темы | 0,35 | 443 / 49 | 0,0001 | 0,01 |
| Поиск: эмбеддинги + реранкер | всегда | 12 поисков | 2 954 / — | входит в замер | 0,03 |
| Черновик для эксперта | только при письме в Службу качества | +1 | — | — | — |
| **Итого на вопрос** | | ≈ 3 вызова модели | | **≈ 0,0075** | **≈ 0,53** |

Токены — замер на 211 вопросах всех типов. Электричество замерено на вопрос целиком и распределено по шагам пропорционально токенам модели. Облако — та же модель Qwen3.8-27B у официального провайдера (Alibaba Model Studio, $0,5 / $3 за 1 млн токенов, курс ЦБ 82,313 ₽/$, без НДС). Расчёт с формулами — [docs/economics.xlsx](docs/economics.xlsx).

- **Нагрузка заказчика.** 100–120 вопросов в день → около 20 ₽ в месяц на ответы. Простой видеокарты круглосуточно — ещё около 470 ₽ в месяц; ночью это время забирает проверка регламентов. Остальной сервер (процессор, память) в замер не входит.
- **Цена вопроса зависит от вопроса.** Вопрос по одной дирекции дешевле, вопрос по нескольким дирекциям дороже: ответ готовится по каждой.
- **Цена и скорость вопроса одинаковы на 4 и на 300 регламентах.** Поиск сначала отбирает лучшие документы по всей базе и подробно ищет только в них, поэтому на любой базе модель вызывается одинаковое число раз. Проверено: на базе в 75 раз больше — столько же поисков и вызовов модели.
- **С базой растут только разовые затраты:** распознавание документа при загрузке и время ночной проверки противоречий — она идёт инкрементально, по изменённым документам.
- **Экономия времени экспертов.** Повторный вопрос закрывается карточкой знания: ноль минут эксперта. Мониторинг повторов показывает, где эта экономия.
- **Оборудование.** Один сервер с потребительской видеокартой RTX 5090 32 ГБ, не серверный ускоритель.

<a id="run"></a>
## Запуск и поставка

```bash
# демо без моделей (BM25 + заглушка модели) — интерфейс и сценарии
python3 -m app.api.server --corpus <папка с регламентами> --data data/app --mock --port 8080

# стенд: помощник + Mailpit
cd deploy && docker compose up -d
```

- `deploy/compose.yaml` поднимает помощника и Mailpit. Сервисы моделей запускаются отдельно и задаются переменными окружения: `LLM_BASE_URL` (OpenAI-совместимый vLLM; на стенде — kv-кэш fp8, контекст 16 384, prefix caching, без рассуждения), `TEI_EMBED_URL`, `TEI_RERANK_URL`, `DOC_INTEL_URL`. Наружу сервисы не слушают, вход — через обратный прокси с паролем.
- После перезапуска видеокарты эмбеддинги поднимаются раньше vLLM: их прогрев требует свободной памяти.
- Подключение компании — конфигурация, а не код: подразделения и документы (`config/documents.json`), адрес почты Службы качества (`QA_EMAIL`, SMTP), темы и мониторинг повторов (веб «Настройки»).
- Анализатор противоречий: `scripts/stand/conflicts.sh <корпус>`; инкрементально — `prev=<metrics.json прошлого прогона>`; по расписанию — строкой crontab в часы наименьшей нагрузки; кандидаты в реестр — `POST /api/conflicts/import`.
- Тесты: `python3 -m unittest discover -s tests`.

<a id="next"></a>
## Что дальше

Основа для каждого шага уже есть в продукте — дальше её расширение.

- **Модуль интеграций — новые источники знаний без изменения логики ответа.** Уже работают doc-intel (20+ форматов) и коннектор Confluence. Следующие коннекторы — справочники компании, разделы частых вопросов, правовые базы по API (КонсультантПлюс, Гарант), инструменты компании по MCP. Дальний горизонт — действия по ответу: завести заявку, отправить на согласование.
- **Внешние источники без утечки.** Наружу уходит только обезличенный общий вопрос, ответ соединяется с регламентом на своём сервере. Обезличивание я уже отработал: модуль защиты идентификаторов перед отправкой данных во внешние модели работает в другом моём продукте. Разбор вопроса здесь уже переформулирует вопрос словами регламента — это первый шаг посредника.
- **Ответ по нескольким дирекциям без пропусков.** Главный источник ошибок на трудных вопросах — потерянная дирекция или исключение. Дальше — выбирать дополнительные пункты кодом, а не моделью: вариант с моделью («Учтите также») я проверил и не включил, он давал ошибки в верных ответах. Опция «Связанные пункты» уже в чате.
- **Несколько вопросов в одном сообщении** — разбор на части и ответ по каждой.
- **Быстрый ответ** — сначала короткий ответ по лучшему пункту, полная проверка и второй проход — в фоне.
- **Ночная подготовка знаний** — для большой базы: вопросы, как их зададут сотрудники, к каждому пункту заранее; кандидаты анализатора, отклонённые перепроверкой, — на решение эксперта, а не в корзину.
